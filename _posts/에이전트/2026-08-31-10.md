## Introduction: 왜 agent eval이 필요한가

좋은 평가는 agent의 품질을 하나의 점수로 증명하는 장치가 아니다. **변경된 행동을 사용자에게 노출하기 전에 발견하고, 운영에서 찾은 실패가 다시 반복되지 않도록 제품의 기억으로 남기는 개발 feedback 장치다.** 평가 없이 문제를 운영에서 발견하고, 원인을 추측해 고친 뒤, 다른 회귀를 다시 운영에서 발견하는 반응형 loop에서 벗어나게 한다.

Agent 평가는 일반적인 single-turn 응답 평가보다 어렵다. Agent는 여러 turn 동안 tool을 호출하고 environment state를 바꾸며, 중간 결과를 관찰한 뒤 다음 행동을 조정한다. **Agent를 유용하게 만드는 자율성, 지능과 유연성이 동시에 평가의 재현성을 어렵게 만든다.**

따라서 agent evaluation은 마지막 응답만 비교하는 문제가 아니다. **어떤 environment에서 무엇을 관찰했고, 어떤 행동을 했으며, 실제로 어떤 상태를 만들었는지를 함께 기록하고 판정해야 한다.** 실패 사례와 성공 조건, grader가 누적될수록 이 평가 자산의 가치는 agent lifecycle 전체에 걸쳐 커진다.

## 이 글이 좋은 이유

Agent evaluation을 이야기하면 benchmark 점수, LLM judge, production monitoring과 simulator가 한꺼번에 등장한다. Anthropic의 글은 이들을 바로 framework 비교로 가져가지 않고, 먼저 평가를 구성하는 기본 단위를 정의한다.

그다음 좋은 task와 grader를 만드는 법, 비결정적인 agent를 반복 측정하는 법, evaluation suite를 장기 운영하는 법으로 범위를 넓힌다. 특정 도구 사용법보다 **무엇을 평가한다고 부를 것인지 공통 언어부터 맞춘다**는 점이 특히 유용하다.

## The structure of an evaluation

Evaluation은 AI system에 입력을 주고, 그 출력에 grading logic을 적용해 성공 여부를 측정하는 test다. 원문은 그중에서도 실제 사용자 없이 개발 과정에서 반복 실행할 수 있는 automated eval을 중심으로 다룬다. Production monitoring과 A/B test, 사용자 feedback은 자동 평가가 놓치는 실제 사용 분포를 보완하는 별도 신호다.

### Single-turn에서 agent evaluation으로

Single-turn evaluation은 prompt에 대한 response를 grading logic으로 판정하는 비교적 단순한 구조다. 반면 agent evaluation은 task와 tool뿐 아니라 실행 가능한 environment를 제공하고, 여러 turn의 agent loop가 environment를 어떻게 바꾸었는지까지 검증한다.

![Single-turn evaluation과 agent evaluation의 구조 비교]({{site.url}}{{site.baseurl}}/assets/images/posts_img/agent-evaluation-series/anthropic-single-turn-vs-agent-eval.png)

*Single-turn evaluation과 agent evaluation의 구조 비교. 출처: [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).*

Agent는 tool을 사용하며 environment state를 바꾸고, 중간 결과에 적응해 다음 행동을 선택한다. 앞선 단계의 작은 오류가 이후 판단에 전파될 수 있기 때문에 마지막 response만으로는 실패 원인을 설명하기 어렵다. **Agent evaluation의 핵심 산출물은 response 하나가 아니라 실행 과정 전체와 마지막 environment state다.**

정상적인 해결 경로도 하나로 고정되지 않는다. Agent가 정적 reference에 없는 더 나은 방법을 찾아도 rigid한 grader는 이를 실패로 판정할 수 있다. 따라서 agent의 실패와 evaluation specification의 한계를 구분하려면 transcript와 outcome을 함께 살펴야 한다.

### 평가를 구성하는 기본 단위

| 원문 용어 | 한국어로 풀어쓴 의미 |
| --- | --- |
| **Task / problem / test case** | 입력과 성공 조건이 정의된 하나의 평가 문제 |
| **Trial** | 같은 task를 한 번 실행한 시도. 출력 변동성을 보기 위해 반복할 수 있다. |
| **Grader** | agent 행동이나 결과의 특정 측면을 판정하는 로직 |
| **Transcript / trace / trajectory** | model output, tool call과 중간 상호작용을 포함한 trial 전체 기록 |
| **Outcome** | trial이 끝났을 때 environment에 남은 최종 상태 |
| **Evaluation harness** | task 실행, 기록, 채점과 집계를 담당하는 평가 인프라 |
| **Agent harness / scaffold** | model이 tool을 호출하고 행동하도록 입력과 실행을 orchestration하는 시스템 |
| **Evaluation suite** | 특정 capability나 behavior를 측정하기 위해 묶은 task 집합 |

여기서 중요한 구분은 evaluation harness와 agent harness다. Evaluation harness는 평가를 실행하는 골격이고, agent harness는 model을 실제 agent로 동작하게 만드는 골격이다. “Agent 성능”을 측정할 때는 model만이 아니라 agent harness의 prompt, tool orchestration과 제약도 함께 평가된다.

![Task, agent, environment, scorer와 artifact로 일반화한 evaluation harness]({{site.url}}{{site.baseurl}}/assets/images/posts_img/agent-evaluation-series/harness-common-model.svg)

## Transcript와 outcome은 같은 것이 아니다

Agent가 최종 응답으로 성공했다고 말해도 실제 environment state가 바뀌지 않았다면 outcome은 실패다. 반대로 기대한 결과를 만들었지만 비효율적인 tool loop나 정책 위반이 있었다면 outcome만으로는 문제를 놓친다.

따라서 두 층을 나눠 본다.

- **Outcome grader**: 최종 파일, database state, test 통과와 실제 부작용을 확인한다.
- **Transcript grader**: tool 사용 순서, 금지 행동, turn 수와 상호작용 품질을 확인한다.

정상 경로가 여러 개인 task에서는 하나의 trajectory를 정답으로 강제하기보다 outcome을 우선 판정한다. 다만 안전 정책이나 반드시 거쳐야 하는 확인 단계처럼 경로 자체가 계약인 경우에는 transcript도 명시적으로 채점한다.

## 세 가지 grader를 조합한다

원문은 agent evaluation의 grader를 크게 code-based, model-based, human grader로 나눈다.

| Grader | 잘 맞는 문제 | 주의할 점 |
| --- | --- | --- |
| Code-based | unit test, exact match, schema, state check와 정량 지표 | 정상 alternative를 지나치게 좁게 막지 않아야 한다. |
| Model-based | 자연어 품질, 복합 rubric과 열린 형태의 결과 | judge calibration, 비용과 model bias를 관리해야 한다. |
| Human | 주관적 품질, 복잡한 정책과 grader 검증 | 느리고 비싸므로 표본 감사와 calibration에 집중한다. |

하나의 grader가 모든 품질을 대표하지 않는다. 예를 들어 상담 agent라면 문제 해결 여부는 state check로, 과도한 turn은 transcript constraint로, 어조는 model 또는 human rubric으로 나눌 수 있다.

Grader 결과를 합치는 방식도 task의 성격에 따라 달라진다. 금지 행동처럼 하나라도 위반하면 안 되는 조건은 binary gate가 맞고, 여러 구성 요소의 달성 정도를 보고 싶다면 partial credit이나 weighted score를 사용할 수 있다. 안전 조건과 품질 점수를 하나의 평균으로 상쇄하지 않는 것이 중요하다.

## Capability eval과 regression eval

두 평가의 목적은 다르다.

- **Capability eval**은 현재 agent가 얼마나 어려운 문제까지 풀 수 있는지 측정한다. 개선 신호를 얻으려면 충분히 어려운 task가 필요하다.
- **Regression eval**은 이미 가능했던 행동이 변경 이후 깨지지 않았는지 확인한다. 안정적으로 통과하는 task도 계속 가치가 있다.

점수가 포화된 capability suite는 더 이상 모델 간 차이나 개선 방향을 잘 보여주지 못한다. 이때 기존 task를 버리는 대신 regression suite로 유지하고, 더 어려운 capability task를 별도로 추가할 수 있다.

## Agent 유형에 따라 성공 조건도 달라진다

### Coding agent

테스트 통과와 repository state 같은 outcome을 code-based grader로 판정하기 좋다. 여기에 불필요한 수정, tool 사용과 코드 품질을 transcript 또는 model grader로 보완할 수 있다.

### Conversational agent

성공이 여러 차원으로 나뉜다. 실제 요청 처리 여부, 제한된 turn 안에 끝났는지, 정책을 지켰는지, 사용자와 적절히 소통했는지를 서로 다른 grader로 확인해야 한다. User simulator를 쓰는 경우 simulator의 행동 품질도 측정값에 들어온다.

### Research agent

정답이 하나로 고정되기 어렵고 출처의 정확성, coverage와 synthesis 품질이 중요하다. 결과 rubric과 citation 검증, 일부 human review의 조합이 필요하다.

### Computer-use agent

화면상의 최종 상태뿐 아니라 클릭과 입력 과정에서 안전 정책을 지켰는지 봐야 한다. 격리된 environment와 재현 가능한 초기화가 평가 신뢰도를 좌우한다.

## 비결정성은 여러 trial로 측정한다

같은 agent가 같은 task를 매번 똑같이 풀지는 않는다. 그래서 task 하나의 단일 pass/fail보다 반복 trial의 분포가 중요하다.

- **pass@k**: `k`번 중 한 번 이상 성공할 가능성. 여러 후보 중 하나만 맞아도 되는 문제에 유용하다.
- **pass^k**: `k`번 모두 성공할 가능성. 사용자에게 반복적으로 안정적인 행동을 제공해야 하는 agent에 중요하다.

첫 시도 성공률이 같아도 반복 횟수가 늘면 두 지표는 반대 방향으로 움직일 수 있다. Product requirement가 “언젠가는 해결”인지 “항상 안정적으로 해결”인지에 따라 선택할 지표가 달라진다.

## 평가를 처음 만드는 Step 0–8

원문의 실무 로드맵을 요약하면 다음과 같다.

### Step 0. 일찍 시작한다

초기 product requirement는 자연스럽게 test case로 옮길 수 있다. Production이 커진 뒤 시작하면 이미 존재하는 행동에서 성공 조건을 역으로 추론해야 한다.

### Step 1. 이미 수동으로 확인하는 것부터 모은다

Release 전에 사람이 확인하는 동작, 자주 쓰는 사용자 task, bug tracker와 support queue의 실제 실패를 초기 dataset 후보로 삼는다.

### Step 2. 모호하지 않은 task와 reference solution을 만든다

Grader가 확인하는 요구사항은 task 설명에서 이해할 수 있어야 한다. 알려진 정상 해법이 모든 grader를 통과하는지 확인해 task와 grader 자체가 작동함을 증명한다.

### Step 3. 균형 잡힌 problem set을 만든다

한 종류의 쉬운 사례나 production failure만 과대표집하지 않는다. 중요한 capability, 난이도, 정상·실패와 product slice를 의도적으로 구성한다.

### Step 4. 안정적인 environment와 harness를 만든다

각 trial을 깨끗한 상태에서 격리하고, 공유된 file·cache·resource 문제가 agent failure처럼 보이지 않게 한다. 실제 production agent와 지나치게 다른 harness도 피한다.

### Step 5. Grader를 신중하게 설계한다

Code, model과 human grader의 장점을 맞는 문제에 사용한다. 지나치게 rigid한 exact match와 모호한 task 때문에 정상 답을 실패시키지 않는지 확인한다.

### Step 6. Transcript를 직접 읽는다

점수만으로는 agent가 틀렸는지 grader가 틀렸는지 알기 어렵다. 여러 trial의 trace와 판정 근거를 읽어 실패가 납득 가능한지 점검한다.

### Step 7. Capability eval의 포화를 감시한다

거의 모두 통과하는 suite는 regression에는 유용하지만 개선 방향을 구분하는 신호는 약하다. 더 어려운 task와 새로운 failure mode를 추가한다.

### Step 8. Suite를 열린 유지보수 대상으로 운영한다

Product, research와 domain expert가 발견한 실패를 기여할 수 있게 하고, 낡거나 중복된 task와 grader를 지속해서 정리한다.

## Offline eval만으로는 완전하지 않다

자동화된 offline eval은 빠른 반복과 release 전 비교에 강하다. 하지만 실제 사용 분포, 예상하지 못한 실패와 주관적 품질을 모두 대표하지는 못한다.

원문은 다음 신호를 함께 사용할 것을 권한다.

- Production monitoring
- A/B testing
- 사용자 feedback
- 사람이 수행하는 transcript review
- 체계적인 human evaluation

이들을 하나의 점수로 억지로 합칠 필요는 없다. Offline eval은 빠른 개발 feedback, production trace는 실제 분포, human review는 자동 grader의 calibration이라는 서로 다른 역할을 가진다.

## 이 시리즈의 고민과 연결하면

이 글은 “최신 업계가 TC 기반을 버렸는가?”라는 질문에 비교적 명확한 답을 준다.

Task 또는 test case는 여전히 평가의 기본 단위다. 달라진 것은 그 task를 단순 input-output fixture가 아니라 environment, agent harness, 여러 grader와 반복 trial을 가진 실행 가능한 문제로 본다는 점이다.

따라서 다음 구조가 자연스럽다.

1. Production trace와 사용자 feedback에서 중요한 failure candidate를 찾는다.
2. 알려진 회귀는 작고 결정적인 replay TC로 고정한다.
3. 상태 변화와 긴 상호작용이 중요한 task는 sandbox나 simulator에서 실행한다.
4. Outcome과 transcript를 서로 다른 grader로 판정한다.
5. 여러 trial과 production monitoring으로 비결정성과 실제 분포를 보완한다.

TC 기반 설계의 반성 지점은 TC를 사용했다는 사실이 아니다. 모든 위험을 하나의 canonical trajectory와 fixture로 표현하면서 curation과 유지보수 비용이 커졌는지, outcome과 environment fidelity를 충분히 다루었는지를 돌아보는 편이 더 정확하다.
