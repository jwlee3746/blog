> 이 시리즈는 실제 제품 환경에서 구축한 평가 시스템의 설계 원칙을 공개 가능한 수준으로 일반화한 기록이다. 모든 다이어그램은 설명을 위한 reference architecture이며, 실제 프로덕션 topology·내부 서비스명·데이터 규모·운영 설정값을 나타내지 않는다.

## 왜 여러 편으로 나눴나

LLM 에이전트 평가는 입력과 출력 한 쌍을 비교하는 문제로 끝나지 않는다. 테스트 데이터의 계약, 여러 모델 판단을 재현하는 방식, 복수 정답 경로의 채점, 장시간 실행의 복구와 비교 가능성까지 서로 다른 설계 문제가 연결돼 있다.

이들을 한 글에 담으면 각 결정의 전제와 trade-off가 묻힌다. 그래서 전체 흐름은 이 허브에서 보여주고, 세부 설계는 네 편으로 나눴다.

## 공통 용어

- **Test case**: 사용자 입력, request context, 예상 경로와 재현에 필요한 tool output을 함께 가진 평가 단위
- **Turn**: 한 번의 사용자 입력에서 시작하는 대화 단위
- **Step**: 에이전트가 action을 결정하는 한 번의 판단 단위
- **Path**: 한 turn 안에서 허용되는 step sequence
- **Projection**: 검증된 test case를 runtime request와 expected path로 분리하는 과정
- **Artifact**: 실행 조건, 실제 결과, 판정과 provenance를 함께 담은 결과물

## 전체 설계 원칙

### 평가 자산도 계약이다

Trace는 좋은 관측 자료지만 그 자체로 버전이 고정된 평가 계약은 아니다. 검토된 test case와 schema를 함께 version control하고, 변경 이유를 코드 리뷰할 수 있어야 한다.

### 검증 경계는 공유한다

CI와 실제 평가가 서로 다른 validator를 쓰면 규칙이 갈라진다. 같은 validation core를 merge 전과 runtime preflight에서 재사용한다.

### 요청과 기대값을 분리한다

과거 step의 tool output은 다음 step을 재현하기 위한 fixture지만, 현재 step의 기대 action은 모델 요청 밖에 있어야 한다.

### 구조화된 행동은 deterministic하게 채점한다

Tool name, parameters, path 같은 구조화된 결과는 규칙 기반으로 비교한다. LLM judge는 자연어 품질처럼 의미 판단이 필요한 영역에 한정한다.

### 실행 조건도 결과의 일부다

Dataset·schema·model·runtime·scoring policy가 다르면 같은 accuracy라도 직접 비교할 수 없다. 결과 artifact에 비교 조건을 함께 남긴다.
