> 이 글은 실제 제품 환경에서 구축한 평가 시스템의 설계 원칙을 공개 가능한 수준으로 일반화한 기록이다. 내부 서비스명, 저장소 구조, 데이터 규모와 운영 설정값은 제외했다.

## 평가 스크립트에서 평가 시스템으로

LLM 에이전트 평가는 처음에는 단순해 보인다. 입력을 모델에 보내고, 나온 도구 호출이 기대값과 같은지 비교하면 된다. 하지만 제품 환경에서는 곧 다음 문제가 생긴다.

- 테스트 케이스마다 request context와 도구 계약이 다르다.
- 하나의 사용자 요청이 여러 번의 모델 판단과 도구 실행으로 이어진다.
- 같은 의도를 만족하는 정상 경로가 둘 이상일 수 있다.
- 모델이나 프롬프트를 비교하려면 실행 조건과 입력을 정확히 고정해야 한다.
- 수천 건을 실행하는 동안 프로세스가 중단되면 처음부터 다시 돌리기 어렵다.
- 결과 숫자만 남기면 왜 실패했는지 재현할 수 없다.

이 단계부터 평가는 일회성 스크립트가 아니라 **버전이 붙은 입력 계약, 실행 엔진, 채점 정책, 결과 artifact를 함께 관리하는 시스템**이 된다.

내가 잡은 목표는 하나였다.

> 같은 테스트 케이스와 같은 실행 정책을 주면, 누가 언제 실행해도 무엇을 비교했는지 설명할 수 있어야 한다.

## 전체 흐름

평가 파이프라인은 다음 경계로 나눴다.

```text
Dataset / Schema change
        │
        ▼
 CI validation ── invalid ──▶ merge 차단
        │
        ▼
 Evaluation preflight ──────▶ 실행 대상·정책 확정
        │
        ▼
 Test-case projection ──────▶ 요청과 기대 경로 분리
        │
        ▼
 Agent execution ───────────▶ multi-step replay
        │
        ▼
 Deterministic scoring ─────▶ 경로별 verdict
        │
        ▼
 Versioned artifact ────────▶ report · 비교 · triage
```

중요한 점은 CI와 실제 평가가 서로 다른 검증 코드를 사용하지 않는다는 것이다. 두 경계 모두 같은 validator를 호출한다. 그래야 CI를 통과한 데이터가 실행 직전에 다른 규칙으로 거부되거나, 반대로 잘못된 데이터가 실제 호출까지 진행되는 일을 막을 수 있다.

## 1. Git의 테스트 케이스를 source of truth로

관측 도구의 trace는 좋은 출발점이다. 실제 요청, 모델 응답과 도구 호출을 한 화면에서 볼 수 있다. 하지만 trace 자체를 평가 계약으로 삼으면 문제가 생긴다.

- 외부 상태에 따라 내용이 바뀔 수 있다.
- 어떤 필드가 필수인지 코드 리뷰에서 알기 어렵다.
- schema와 scoring policy의 변경을 같은 revision으로 묶기 어렵다.
- 특정 시점의 평가 population을 다시 만드는 비용이 커진다.

그래서 trace는 **import source**로만 사용하고, 검토가 끝난 테스트 케이스는 Git에 JSON으로 저장했다. 테스트 케이스 하나를 파일 하나로 두면 변경 이유와 리뷰 범위가 명확해지고, dataset·schema·validator를 같은 pull request에서 바꿀 수 있다.

각 케이스에는 다음 정보가 함께 있어야 한다.

- 사용자 입력과 locale·시간·기기 같은 request context
- 예상하는 agent action과 tool parameters
- 다음 step을 재현하는 데 필요한 실제 tool output
- 허용되는 alternative path
- 데이터 출처와 변환 근거를 확인할 provenance

여기서 tool output은 임의로 만들어 넣지 않는다. 다음 판단이나 최종 응답을 재현하는 데 필요하고, trace나 계약으로 근거를 확인할 수 있을 때만 fixture로 고정한다.

## 2. JSON Schema와 관계 검증을 분리

테스트 계약은 JSON Schema로 관리했다. TypeScript interface를 별도의 source of truth로 만들지 않았다. 계약이 두 벌이면 시간이 지날수록 둘 중 하나가 뒤처지기 때문이다.

검증 순서는 다음과 같다.

1. 파일 읽기와 JSON parse
2. JSON Schema 검증
3. canonical formatting
4. step ID·response reference 같은 파일 내부 관계
5. 디렉터리 topology와 파일명 규칙
6. 파일 사이 identifier 중복

Schema가 값 하나의 shape를 책임한다면, validator service는 여러 필드나 파일 사이의 관계를 책임한다. 예를 들어 “이 response reference가 이미 끝난 step을 가리키는가”는 JSON Schema만으로 읽기 좋게 표현하기 어렵다. 반대로 이런 관계 규칙 때문에 schema를 약하게 만들면 기본 계약까지 흐려진다.

Validator는 자동으로 파일을 고치지 않고 issue만 반환한다. 평가 자산을 조용히 정규화하면 실제로 어떤 데이터를 평가했는지 알기 어려워지기 때문이다.

## 3. 기대값을 요청에서 분리하는 projection

multi-step 평가에서 가장 주의한 부분은 **정답 누출**이었다.

N번째 모델 판단을 재현하려면 이전 step의 사용자 메시지, tool call과 tool output이 conversation history에 들어가야 한다. 하지만 N번째 step의 기대 action까지 요청에 섞이면 평가가 무의미해진다.

따라서 검증된 테스트 케이스를 바로 실행하지 않고, 먼저 다음 두 요소로 projection했다.

- 모델에 전달할 request plan
- request 밖에서 채점에만 사용할 expected path

Step 0은 사용자 요청으로 시작한다. Step N의 request에는 `0..N-1`의 고정된 history만 누적된다. Preferred path와 alternative path는 각자의 history를 독립적으로 만든다. 이 경계 덕분에 실행 엔진은 원본 JSON 구조를 알 필요가 없고, 채점기는 네트워크 요청을 만드는 방법을 알 필요가 없다.

## 4. 구조화된 행동은 deterministic하게 채점

도구 호출처럼 구조화된 결과는 가능한 한 deterministic하게 비교했다.

- action 또는 tool name
- 선택된 agent
- 필요한 function
- parameters
- 실행 tier나 skill 사용 여부처럼 별도의 평가 차원

최종 자연어 응답의 품질처럼 의미 판단이 필요한 항목에는 LLM judge를 사용할 수 있다. 하지만 구조화된 action까지 judge에 맡기면 같은 결과가 실행마다 달라지고, 비용과 latency도 증가한다.

정상 경로가 여러 개인 케이스는 요청을 복제하지 않고 alternative path로 표현했다. Preferred path가 통과하면 불필요한 alternative 실행을 생략하고, 실패했을 때만 다음 경로를 평가한다. 이렇게 해야 “여러 정답을 허용한다”와 “동일 케이스를 여러 번 센다”를 구분할 수 있다.

## 5. 내부 discovery와 최종 action을 구분

에이전트는 최종 도구를 바로 호출하지 않고, 사용할 capability나 skill을 먼저 찾기도 한다. 이 discovery step을 무조건 실패로 채점하면 실제로는 정상적인 실행을 오답으로 분류하게 된다.

그래서 예상하지 않은 discovery-only 응답이 왔을 때는, 실행기가 반환한 message와 snapshot을 그대로 다음 요청에 이어 붙여 최종 action까지 진행하도록 했다. 단, 다음 조건에서는 즉시 실패시켰다.

- discovery와 최종 action이 비정상적으로 한 응답에 섞임
- discovery 결과나 tool result가 누락됨
- 기대한 capability가 아닌 다른 capability를 로드함
- continuation 횟수가 설정된 예산을 넘음

리포트에서는 최종 action만 맞았는지뿐 아니라 직접 실행했는지, 기대한 skill을 읽고 실행했는지도 구분한다. 제품 동작은 같아 보여도 내부 실행 경로가 의도와 다른 문제를 발견하기 위해서다.

## 6. 장시간 평가를 운영 가능한 작업으로

대규모 평가에서는 모델 정확도만큼 실행 안정성이 중요하다. 네트워크 오류나 프로세스 종료 한 번으로 전체 run을 잃지 않도록 다음을 추가했다.

### Checkpoint와 resume

일정 개수의 실행이 끝날 때마다 결과를 원자적으로 저장한다. 종료 신호를 받으면 새 요청 dispatch를 멈추고, 진행 중인 요청이 정리된 뒤 마지막 checkpoint를 남긴다.

Resume은 단순히 같은 파일 경로를 믿지 않는다. 테스트 케이스 경로, ID, 반복 index와 projected plan의 digest로 실행 identity를 만든다. 입력이나 기대 경로가 바뀌었다면 과거 결과를 재사용하지 않는다.

### 실행 예산

동시 요청 수와 요청 시작 간격을 별도로 관리한다. 동시성은 실행 자원 보호를, 시작 간격은 provider quota 보호를 담당한다. 둘을 하나의 sleep 값으로 합치면 local model과 remote provider의 서로 다른 제약을 표현하기 어렵다.

### Provenance

결과 artifact에는 score뿐 아니라 다음을 남긴다.

- dataset과 schema revision
- 실행한 모델·provider·tier
- evaluator와 대상 runtime revision
- validation·selection·scoring policy
- 각 step의 실제 구조화 결과와 오류

그래야 두 artifact의 정확도가 다를 때 모델 변화인지, dataset 변화인지, 실행 정책 변화인지부터 확인할 수 있다.

## 7. 구조화 과정에서 지킨 것

기존 평가 기능을 새 구조로 통합할 때 한 번에 다시 쓰지 않았다. 먼저 동일한 입력에 동일한 판정을 내리는 parity fixture를 만들고, validator → loader → transport → scorer → executor → CLI 순서로 책임과 의존 경계를 분리했다.

새 경로가 baseline과 비교 가능한 상태가 된 뒤 legacy entry point와 일회성 변환 도구를 제거했다. 마이그레이션 중에 호환 코드를 core contract에 섞지 않고 별도 adapter에 가둔 것도 중요했다. 오래된 형식을 읽어야 한다는 이유로 새 schema를 느슨하게 만들면 migration이 끝난 뒤에도 복잡성이 남기 때문이다.

## 배운 점

이 작업에서 얻은 결론은 다음과 같다.

1. **평가 데이터도 제품 코드처럼 계약과 리뷰가 필요하다.** 숫자를 만드는 입력이 신뢰할 수 없으면 결과도 신뢰할 수 없다.
2. **검증 경계는 하나여야 한다.** CI와 runtime이 같은 validator를 공유해야 규칙이 갈라지지 않는다.
3. **재현과 정답 누출 방지는 함께 설계해야 한다.** 이전 tool output은 fixture지만 현재 expectation은 요청 밖에 있어야 한다.
4. **구조화된 결과는 deterministic하게 비교한다.** LLM judge는 의미 평가가 필요한 곳에만 사용한다.
5. **평가 실행도 운영 시스템이다.** checkpoint, budget, provenance가 없으면 대규모 run을 반복 가능한 실험으로 다루기 어렵다.
6. **마이그레이션은 parity를 먼저 만든다.** 새 언어로 옮기는 것보다 기존 판정을 설명 가능하게 보존하는 것이 우선이다.

결국 좋은 평가 파이프라인은 정확도 한 줄을 만드는 도구가 아니다. 입력 계약부터 실행 조건, 경로별 판정과 실패 근거까지 남겨 다음 의사결정의 비용을 낮추는 시스템이다.
